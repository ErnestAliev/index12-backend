# Устойчивое выполнение INDEX12 → Codex → MCP

Протокол 2, API/MCP 3.4.0. Один логический журнал на чат; отдельное выполнение каждого сообщения и отдельное подтверждение каждого изменения. Состояние не привязано к PID, временному файлу или открытому окну desktop.

## Идентификаторы и доверенная привязка

Worker создаёт `mcpExecutions` до отправки сообщения. После `turn/start` сохраняет полученные от App Server `threadId`/`turnId`. MCP читает `_meta["x-codex-turn-metadata"]` из конверта протокола; аргументы модели не задают привязку и не предоставляют права. Проверка на живом App Server подтвердила передачу этих полей и для вызовов из code mode.

Запущенный MCP использует постоянный режим `INDEX12_MCP_EXECUTION_MODE=durable`. Между сообщениями его окружение не меняется. Worker не пытается обновлять путь к файлу через `thread/resume`.

Каждая запись API проверяет actor/workspace, действующее выполнение и аренду worker. Проверка и изменение затрагивают документы выполнения и worker в той же транзакции: отмена или захват аренды конфликтуют с поздней записью. Завершение старого worker закрывает только его выполнения. Отсутствующая/устаревшая метаинформация блокирует действие, без перехода в незащищённый режим.

Обычные подключения MCP из других чатов сохраняют прежние разрешения и получают устойчивые подтверждения API; отсутствие web-привязки не создаёт фиктивного web-выполнения.

## Атомарные действия

Создание, изменение, удаление доходов/расходов/переводов и изменение начального остатка проходят через существующий transactional history engine. Финансовая запись, история, `mcpActions` и ссылка из `mcpExecutionEvents` коммитятся вместе. Ошибка подтверждения откатывает изменение. Socket.io-события отправляются после коммита.

`mcpActions` хранит один результат действия. События сообщений ссылаются на него, не копируя полный результат. Повторная доставка возвращает сохранённый ответ с `replayed=true`; это подтверждение прежнего действия, а не утверждение о неизменности текущей записи. Перед новой правкой остаётся обязательным свежее чтение и `expectedVersion`.

HTTP-клиенты могут передавать `Idempotency-Key` (8–160 символов). При его отсутствии создание использует существующий `idempotencyKey`, PATCH/DELETE — каноническое тело с версией и маршрутом. Один явный ключ с другим телом отклоняется. Повторное чтение результата также проверяет текущие права на счета и владельца операции.

Импорт сохраняет существующую модель возобновляемых шагов и `planToken`: это намеренно не одна транзакция на весь импорт. Перед каждым шагом проверяется выполнение; сами вызовы обработчиков проходят транзакционную проверку аренды. `mcpImportRequests` связывает выполненные/частичные импорты с сообщениями, сохраняя прежнее поведение `IMPORT_PARTIAL_FAILURE` и повтор с тем же планом.

## Завершение и восстановление

Состояния: `running`, `completed`, `failed`, `interrupted`. Ошибка закрывает только текущее выполнение; новое сообщение получает новый ID. Таймаут и разрыв соединения сначала инициируют блокировку новых записей и прерывание хода, а затем возвращают управление очереди. Записи пользователя автоматически не отправляются повторно.

При потере HTTP-ответа действие может быть уже выполнено. Worker собирает отчёт из базы; отсутствие ответа не трактуется как отсутствие изменения. После перезапуска прежние выполнения закрываются, подтверждения сохраняются. Старый вызов не может быть присоединён к новому сообщению.

`desktopJobs`, временные вопросы и неотправленные вложения сохраняют существующую очистку. На `mcpExecutions`, `mcpActions`, `mcpExecutionEvents` не устанавливается TTL: это компактная история действий, а не транспортный кэш. Долговременная очистка финансового аудита должна задаваться отдельной политикой хранения.

`GET /api/codex/chats/:id/executions` возвращает журнал принадлежащего пользователю чата; `GET /api/codex/jobs/:id` восстанавливает подтверждения из журнала после удаления временного задания. Проверки actor/workspace выполняются и на чтении.

## Обновление

1. Развернуть backend с `executionProtocol=2` в `/api/mcp/status`.
2. Перезапустить локальный worker после завершения активного задания. Если backend ещё старый, worker явно останавливает отправку нового сообщения.
3. Для существующего чата worker один раз создаёт attached fork завершённой истории и переводит тот же чат INDEX12 на новый runtime. Источник сохраняется, скрытая связанная сессия не дублирует обычный список Codex. Активный thread не мигрируется. Далее процесс остаётся живым между сообщениями. Причина такого перехода: установленный App Server не поддерживает `thread/unload`; `thread/unsubscribe` сохраняет runtime на период неактивности и не гарантирует перезапуск MCP.

Новых секретов, переменных Render и миграции финансовых операций не требуется. Коллекции и индексы создаются автоматически. Требуется replica set/Atlas с транзакциями, как и для существующей истории изменений.

## Проверки

`npm test` — модульные и HTTP-проверки. `node tests/integration/mcp.cjs` — полный существующий MCP-набор с disposable replica set, production-схемами и обработчиками.

`node tests/integration/durable-execution.cjs` — несколько сообщений через один MCP, повтор результата, старый turn, конфликт версии, откат при недоступном подтверждении, потерянный HTTP-ответ, смена worker, история после TTL заданий и изоляция доступа. `--app-server` дополнительно проверяет последовательные сообщения и миграцию runtime с сохранением истории в настоящем чате Codex с production MCP/API на синтетических данных. Совместимый прежний вход: `node tests/integration/mcp-execution.cjs --app-server`.

Финансовые данные рабочей области пользователя для проверок не изменяются.

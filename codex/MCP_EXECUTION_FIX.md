# Сбой разрешённой записи MCP INDEX12

## Подтверждённая первопричина

В `2026-10-30T20:40:37.940571Z` App Server получил от клиента связки JSON-RPC ошибку `-32000`. Следующая строка журнала содержит исходное сообщение клиента: «Требуется подтверждение в desktop-приложении». В журнале обработки разрешений зафиксировано `ResolveElicitation ... decision: Decline`. В `20:40:37.943Z` вызов `index12_update_operation` завершился `status=failed`, `duration=0` и сообщением `user rejected MCP tool call`.

Источник — прежняя ветка обработки входящих server requests в `codex/codexClient.cjs`: любой запрос с `id` автоматически получал ошибку. Пользовательский текст доходил до Codex, но клиент не согласовывал серверный режим `direct` с маршрутом проверки разрешений App Server. App Server преобразовал техническую ошибку клиента в отказ. Подтверждения реального нажатия пользователем «Отклонить» нет. Вызов остановился на стороне разрешений до исполнения инструмента и HTTP-записи. Исходный пакетный скрипт корректно остановился по `isError`, остальные изменения не запускались.

Источники диагностики — локальный rollout соответствующего разговора, `app-server-daemon/daemon.stderr.log`, таблица `logs` локального журнала Codex и исходный код клиента. Секреты и содержимое других финансовых операций в отчёт не включены.

## Исправление

- Перед web-ходом worker получает свежие capabilities и режим подтверждения из аутентифицированного API, проверяет совпадение actor/workspace.
- Только разрешённые инструменты при `direct_on_user_request` получают режим `auto`; App Server использует `approvalsReviewer=auto_review`. Исходный запрос пользователя и история передаются без выдуманного согласия. Автоматическая проверка намерения, реальные отказы, managed policy, права API и sandbox сохраняются. `approve` и `approvalPolicy=never` не используются.
- Дополнительные вопросы теперь передаются в чат и ожидают фактического ответа пользователя. Неизвестные/защищённые протоколы возвращают конкретное ограничение `APPROVAL_UNAVAILABLE`. Старое неоднозначное `user rejected MCP tool call` отображается как `APPROVAL_UNRESOLVED`, если нет доказанного решения пользователя. Настоящий decline, cancel, блокировка политикой, `FORBIDDEN`, ошибка API и `VERSION_CONFLICT` различаются.
- Записи web-хода сериализуются. Первая ошибка закрывает приватный журнал выполнения до возврата `isError`. Следующие записи блокируются `EXECUTION_STOPPED`, включая пакетный код, игнорирующий ошибку. App Server получает `turn/interrupt`.
- Сохраняется исходная защита `expectedVersion`; автоматической подстановки новой версии и повторного запроса записи нет.
- В failed job передаётся отчёт с подтверждёнными успешными результатами. Интерфейс не использует текст неподтверждённого «успеха». При чтении истории заявления модели в ходе с ошибкой заменяются отчётом по результатам инструментов. Неподтверждённый ответ API не считается доказательством отсутствия записи: перед повтором требуется свежее чтение.

## Дополнение: доставка вопросов в чат и полный набор MCP

После отдельной пользовательской команды шесть финансовых правок были успешно выполнены пользователем через чат. Затем Codex обратился к интерфейсу для начального остатка: дополнительный запрос MCP elicitation в `2026-10-30T21:10:31.800110Z` попал в прежний fallback клиента, поскольку канал интерактивных вопросов ещё не был реализован. Успех шести правок не отменяется последующей ошибкой; повтор этих правок для диагностики не выполнялся.

Добавлен сквозной канал App Server → worker → `desktopRequests` → API → карточка вопроса → ответ API → исходный native request. Нет автоматического согласия. Схема ответа проверяется сервером, разрешения ограничиваются исходным запросом и текущим ходом. Другой пользователь/рабочая область, старый worker, просроченный вопрос и повторный ответ не могут разрешить действие. Ответы удаляются из временной записи после доставки. Закрытие/открытие чата возобновляет ожидание того же задания без повтора команды.

По явному запросу пользователя включены все 13 существующих инструментов MCP INDEX12 в конфигурации Codex и в конфигурации чата. Каталог обновлён без вызова финансовых инструментов. Проверено в существующем разговоре: удаления, создание и редактирование переводов доступны; аутентифицированный API подтверждает роль admin и capabilities create/update/delete/createTransfers/updateTransfers/executeImport=true, confirmationMode=direct. Наличие инструментов не создаёт ещё не реализованные функции API.

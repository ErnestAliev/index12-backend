# Универсальные операции 1С через INDEX12

Владелец/admin текущей рабочей области получает эти инструменты в удалённом MCP, облачном Codex и локальном stdio-коннекторе:

| Инструмент | Действие |
| --- | --- |
| `index12_onec_status`, `schema`, `query`, `get_object` | Публикация, метаданные, справочники и документы |
| `index12_onec_create_object` | Новый непроведённый документ или элемент опубликованного ссылочного справочника |
| `index12_onec_update_object` | Частичная правка реквизитов, полный итоговый массив табличной части |
| `index12_onec_set_posted` | Проведение / отмена проведения документа по отдельному поручению |
| `index12_onec_set_deletion_mark` | Пометка / снятие пометки удаления; перед пометкой обязательная форма подтверждения |
| `index12_onec_mutation_status` | Проверка сохранённой операции без повторной записи |

Поддерживаются опубликованные ссылочные объекты с единственным ключом `Ref_Key`: документы, справочники, планы счетов/характеристик/видов расчёта, планы обмена, задачи и бизнес-процессы. Составные ключи записей регистров и произвольные HTTP-команды не выдаются за универсальный CRUD. Физическое удаление не выполняется: используется стандартная `DeletionMark`.

## Проверки записи

- Роль admin и нужный scope create/update/delete, актуальные права рабочего пространства и выполнения. Доступ сотрудников через `team_chat_read` остаётся только для чтения.
- `ONEC_WORKSPACE_ID` и подключение выбираются сервером; `companyId` должен быть связан с организацией именно этой базы. Организация документа не переносится скрытно. Каталоги без поля организации используют ту же проверенную связь компании с базой.
- Поля и типы проверяются по `$metadata`. GUID-ссылки разрешаются через опубликованные `NavigationProperty` / `Association`, читаются в своей реальной коллекции и проверяются на доступность. Для старого кэша сохранены известные стандартные связи. Составная ссылка передаётся вместе с `_Type`.
- `Ref_Key`, `DataVersion`, `Posted`, `DeletionMark` и предопределённые системные поля не принимаются в произвольном data. Новый GUID назначает сервер до POST; документ создаётся непроведённым, без пометки удаления. Date и наименование каталога не придумываются.
- Счёт покупателю проверяет контрагента, договор, валюту, строки, количество × цену, итог и НДС по выбранной реальной ставке, без зашитой законодательной ставки.
- PATCH использует точную `DataVersion` в `If-Match`; после записи читаются GUID, организация и переданные поля. При сверке таблиц учитываются все строки, но добавленные сервером служебные поля не создают ложную неопределённость.

1С не вызывает стандартную проверку заполнения при записи через OData, поэтому существенные проверки выполняет INDEX12. Права самой учётной записи 1С всё равно проверяются платформой: наличие метаданных не означает подтверждённое право создавать объект. См. [официальное описание REST](https://kb.1ci.com/1C_Enterprise_Platform/1C_Enterprise_Platform_Overview/Integration/REST_interface/).

## Повторы и подтверждения

`operationId` сохраняется для одного поручения. Журнал `onecObjectMutations` хранит назначенный GUID, поля, состояние и привязку к cloud/desktop-выполнению без TTL. Повтор того же успешного запроса возвращает результат без POST; изменённые параметры с тем же UUID отклоняются. При таймауте вызывается только `mutation_status`: отсутствующий GUID не разрешает создавать дубль новым ключом. Подтверждённые создания попадают в журнал Codex как `index12_onec_create_object`.

Перед `marked=true` MCP читает актуальный объект, сверяет версию и получает отдельное явное approve=true через elicitation. Direct не пропускает этот шаг. Отказ, отмена, устаревшая версия или недоступная форма не меняют объект и останавливают выполняемую цепочку. Снятие пометки не требует подтверждения удаления. Произвольный create/update не позволяет обойти эту форму через DeletionMark.

Готовая покупка по PDF поставщика продолжает использовать `prepare_purchase` / `execute_purchase` с исходящим поручением и задачей о закрывающих. Универсальное создание не объявляет документ проведённым или оплаченным.

## Клиенты и проверки

Явный `mcp_servers.index12.enabled_tools` должен включать инструменты 1С: серверный tools/list не отменяет клиентский allowlist. После изменения локального подключения требуется Restart MCP в приложении; для установленного HTTP-плагина — Refresh tools, если каталог ещё старый. См. [OpenAI MCP](https://learn.chatgpt.com/docs/extend/mcp) и [управление инструментами плагина](https://developers.openai.com/api/docs/guides/custom-mcp-server).

- `node --test tests/onec-generic.test.cjs` — метаданные ссылок, сверка строк, суммы/НДС и обязательное подтверждение удаления.
- `node tests/integration/onec-purchases.cjs` — отдельная MongoDB и имитация 1С, реальная опубликованная схема покупательского счёта, создание/правки таблиц/справочников, версии, ACL, журнал, таймауты с записанным и отсутствующим GUID, отсутствие повторного POST; прежняя цепочка покупки и редактирования.
- `npm test`, `node tests/integration/cloud-chat.cjs`, `node tests/integration/cloud-recovery.cjs` — регрессии MCP и облачного Codex. Рабочие документы в проверках не создаются.

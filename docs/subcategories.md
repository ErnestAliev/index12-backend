# Подкатегории операций

`Subcategory` — отдельная коллекция: `name`, `nameKey`, `parentCategoryId`,
`userId`, `workspaceId`, `order`. Название уникально внутри категории и владельца
пространства без учёта регистра. Одинаковые названия в разных категориях допустимы.

У `Event` появилось необязательное поле `subcategoryId` (ссылка на `Subcategory`,
по умолчанию `null`) и индекс `(userId, subcategoryId, date)`.
Перезапись старой истории не требуется: операции без нового поля продолжают
работать и попадают в группу «Без подкатегории». Их можно дополнить обычным PUT.
Изменение подкатегории не меняет сумму платежа или баланс счёта.

API:

- `GET /api/subcategories`: справочник текущего пространства.
- `POST /api/subcategories`: `{ name, parentCategoryId }`; создание доступно
  администратору и менеджеру, повтор того же названия возвращает существующую запись.
- `PUT /api/subcategories/:id`: `{ name }`; переименование администратором.
- `DELETE /api/subcategories/:id`: удаляет детализацию и снимает её с операций,
  сохраняя сами операции, суммы и категории.
- `POST /api/events`, `PUT /api/events/:id`, `POST /api/transfers`: принимают
  `subcategoryId`. Сервер проверяет родителя и принадлежность пространству.
  Если старый клиент меняет категорию без нового поля, несовместимая подкатегория
  сбрасывается. Некорректный явный выбор отклоняется.

Расходы с несколькими категориями могут выбрать подкатегорию одной из выбранных
категорий. Одна операция учитывается в детализации один раз. Родители проектных
разбиений исключены из сумм; изменение детализации родителя переносится на доли.
Переводы имеют отдельный оборот и не прибавляются к доходам или расходам.
Факт, план, период и видимость счетов применяются до группировки на клиенте.
Серверный snapshot возвращает `subcategoryTotals`.

Формы дохода, расхода и перевода позволяют выбрать или создать подкатегорию.
В редакторе справочников есть вкладка «Подкатегории». В журнале доступны отдельная
колонка, фильтр и редактирование; в графиках — отдельные диаграммы, а в виджетах —
детализация доходов, расходов и переводов. Экспорт/импорт сохраняет подкатегорию.

Развёртывание: сначала обновить backend, затем frontend. Коллекция и индексы
создаются Mongoose; миграцию старых финансовых документов запускать не нужно.

Проверки:

```sh
npm test
node tests/integration/subcategories.cjs
node tests/integration/subcategories.cjs --browser
```

Интеграционная проверка требует `mongod` в PATH (или `MONGOD_BIN`), запускает
собственную MongoDB на 127.0.0.1:27028 во временном каталоге и удаляет её после
завершения. `.env` не загружается, рабочая база не используется. Флаг `--browser`
требует соседний checkout `index12-frontend` с установленными зависимостями и Chrome
(или `SCROLL_TEST_CHROME`). Проверка использует реальные схемы и обработчики API,
а также реальные формы, тултипы, виджеты и журнал в браузере.

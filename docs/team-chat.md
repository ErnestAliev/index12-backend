# Internal employee chat

The `/api/team-chat` router provides a workspace-scoped chat alongside INDEX12. Owners use their existing INDEX12 session; invitees use a separate persistent phone/password session at `/team/:token`. A phone session never authenticates the user to financial APIs. Joining requires an owner decision. Chat roles do not modify workspace roles.

The owner starts as `manager`; chat settings allow `employee`, `manager`, and `director`. Only owners issue invites and assign/revoke roles. Phone numbers normalize to E.164; passwords use random salts and scrypt. Authentication attempts are limited in MongoDB. Membership and workspace access are checked on every request. Chat credentials use a separate HttpOnly, SameSite=Lax cookie scoped to `/api/team-chat`; only its SHA-256 hash is kept in `teamChatSessions`. The cookie expires after a year and renews during use. Explicit logout revokes this device's token. Existing express chat sessions migrate automatically. Closing or hiding the chat does not log out; the standalone employee screen offers an explicit logout control. Chat login does not replace a signed-in INDEX12 session. Files are scoped, downloaded as attachments, limited to five files and 25 MB per message, 10 MB per file. Unlinked uploads expire after one day.

Employees create requests with a title (free text or a suggestion from the scoped expense-category catalog), formatted amount, payment date, a selected or newly created workspace contractor, and an optional comment. The selected category is validated on the server and retained for manager preparation. They do not choose our company or account. Owner identity and the current chat role are shown in the header; only the owner can select their own employee/manager/director role in Members. Ownership is verified from the INDEX12 account and workspace, takes precedence over a staff cookie, and grants an independent `manageMembers` capability; selecting any chat role never removes owner administration. Administration is independent from the displayed role: an owner in any chat role can prepare, recall and record approved requests. The creator defaults to manager and administrator; roles persist in Mongo settings and refresh through state updates. The composer is shared with Codex. The header combines the current name, role and logout in one row; navigation is a grouped tab list below it. Success notices expire and do not reserve content height. The mobile request form uses 16px inputs, a formatted payment date, a sticky submit action above the visual viewport keyboard, and scrolls focused fields clear of that action. Directory suggestions flip above/below the field according to available space. Request cards show title, amount and current status; deletion and copying use icon controls, and author/contractor/date/history are collapsed behind the information control.

When a PDF is sent, only its sender gets the invoice-processing question. Confirmation calls the server's OpenAI Responses integration using the existing `OPENAI_API_KEY` and `OPENAI_CHAT_MODEL`, with PDF input, a strict extraction schema, no tools, and `store: false`. Supplier and buyer remain distinct. Parties match by a unique BIN or exact normalized name; conflicting BINs are not overwritten. Expense categories and subcategories are suggested only from the workspace catalog. The original PDF remains attached. File ID and content hash prevent duplicate requests. Recognition failures are reported; they do not manufacture financial operations.

Expense requests follow `manager_review → director_review → ready → recorded`, or `rejected`. Decisions require the current role and expected version. All active members see the same Messages and Requests tabs; only the owner sees Members. Approval controls still follow the request stage. A separate forecast includes all active requests, including those not yet submitted.

The owner acting as manager can drag a request onto a timeline cell or open its preparation form. Missing details use the existing expense editor: account, company, account owner, categories/subcategory, projects, contractor, date, amount, description and optional comment. Enrichment creates a virtual draft chip, not a financial Event. Drafts reserve cells across GUI and MCP operations under the existing transaction/lock. The manager can save the draft or submit the full snapshot to the director. Saves are single-flight in the editor and use a mutation ID/hash for safe retries. A failed UI refresh after a committed save is not reported as a failed mutation. Genuine version conflicts retain the form, disable submission and offer explicit loading of current details. Success shows the payment date and account. Submitted details are frozen; recall is required to edit them and reallocates a cell if needed. Cards show the approval chain and decision history. The current first release lets the owner acting as manager convert a fully approved request into a real expense using the existing audited operation handler. A selected account must belong to that request's company. The request and operation commit together, conversion retries return the existing operation, and timeline placement uses a free cell within 32 visible cells.

The Tasks tab has a separate cash forecast: all active requests, including unapproved requests, reduce projected cash on their requested payment date. Rejected and converted requests are excluded. Existing scheduled INDEX12 operations are included up to the latest request date. Company cash pools stay separate. Each account shows its current balance, requests awaiting approval, fully approved requests, and the balance after all allocated requests. Request cards show the selected account and its balance after that request and after all requests. Requests without an assigned company are shown as unallocated costs and never charged to an arbitrary company. This forecast is in chat. Prepared virtual request chips appear on the timeline, while the main dashboard's financial totals still use real operations only. Existing entries remain the source of current balances; an expense entry does not prove bank payment.

Messages expose actions on a 450ms hold, right-click or the keyboard context-menu key. Moving or scrolling cancels the hold. The menu includes edit (author only), forward, copy, delete, six toggleable reactions and stage-appropriate approval/rejection. Permanent per-message delete/copy buttons are removed. Menus have text labels, keyboard focus containment and theme-aware surfaces.

Message approvals are independent of financial requests: manager approval forwards to director review, director approval completes the chain, and rejection ends it. Owner administration permits acting at either stage. Each decision records actor, name, stage, text revision and time. Editing increments the text revision and clears current approval, retaining its prior snapshot in a private edit audit. Approval never implicitly creates an expense. Reactions are per actor and do not invalidate a text editor. Incremental state updates refresh edits, approvals and reactions in cached history.

Forwarding offers the current shared chat and other workspaces verified as owned by the authenticated INDEX12 account. Chat-only guests can forward within their current shared chat. Source attribution is retained, approvals/reactions are not copied, attachments are cloned into the target scope, and replaying the same forward key does not create duplicates. This does not grant access to another workspace or expose participant phone numbers.

Members can delete their own messages; the owner can moderate all messages. Requests can be deleted by their author before recording and by the owner/reviewers. Deletion keeps an audit tombstone, removes request reservations and forecast costs, and never deletes an already recorded financial Event. Deleted messages are removed from cached history as well as the current page.

The chat link uses a workspace-specific web manifest proxied at `/team-manifest/:token`, whose `start_url` retains the original `/team/:token` invitation route. Existing shortcuts created with the old generic manifest need to be added again. Browser storage clearing or explicit logout can still require authentication; the implementation does not claim control over operating-system cookie deletion.

Messages update through authenticated SSE, with reconnect/focus recovery and a 15-second fallback. SSE carries invalidation only. Owners see an in-app join approval dialog above other windows. This dialog does not claim OS push delivery when INDEX12 is closed. No SMS or WhatsApp provider is used. Password recovery is approved only by the verified workspace owner after checking the employee through a known contact.

Read-only chat state excludes password material and returns 50 messages with a compound timestamp/ID history cursor. The most recent 500 request cards are shown with explicit truncation; the forecast always includes all active requests.

- `node tests/integration/timeline-slots.cjs`

- `node tests/integration/team-chat.cjs --browser` (uses the sibling frontend repository, isolated MongoDB and headless Chrome)

## Invite onboarding and device notifications

The standalone chat is named **Chat**, with a speech-bubble **12I** icon (192/512 PNG, safe maskable area, Apple touch icon). The invitation manifest keeps its workspace identity and original invitation URL. A first mobile visit offers installation: supported browsers invoke `beforeinstallprompt` from a user tap; iPhone displays the native Share → Add to Home Screen steps. Installation is only confirmed by standalone mode or `appinstalled`. A site cannot silently install a Home Screen icon. The setup dialog can be reopened through the header bell; it does not occupy message space.

Invitations store the owner's name and proposed chat role. Existing invitations default to employee and resolve the workspace owner's name. The proposal never bypasses pending approval or grants administration. Only the verified owner creates invitations. The phone form fixes +7 outside the editable national number, groups ten digits as `701 123 45 67`, and accepts pasted +7/8 numbers. Registration and resumed login show the real workspace and role; persistent sessions remain subject to browser/OS storage retention.

Initial history has a loading/retry state and retrieves the latest 50 messages. `GET /messages?before=<messageId>` returns only the next history page, with a compound createdAt/ID cursor, decorations and hasMore. It excludes deleted rows and private edit audit. Scrolling near the top loads one page at a time and retains the visible message anchor. Loaded history is not silently capped at 1000 messages. Reconnect gaps exceeding the latest page are exposed and recovered in bounded pages. State refresh watches the latest page and visible history IDs (at most 150) for edits/deletions, avoiding growing query strings.

Chat Web Push uses its own `/team-sw.js` registration, scoped to `/team/`; it never replaces the calendar service worker or caches authenticated history. Public `/push-config` exposes only configured status and the public VAPID key. Authenticated `/push/key`, `/push/subscriptions` (POST/DELETE) and `/push/test` also work while awaiting approval. The subscription is bound to the verified chat identity and original valid invite, not caller-supplied workspace/actor fields. Pending members receive no chat content. Explicit tests target only the current device and are rate limited. The client confirms server registration and separately checks receipt of the test notification; gateway acceptance alone is not reported as delivery. Permission is requested only from a user gesture; iPhone requires the Home Screen app. Every entry/focus rechecks permission and the device subscription without repeated permission prompts.

Configure `TEAM_CHAT_VAPID_PUBLIC_KEY` and `TEAM_CHAT_VAPID_PRIVATE_KEY` as Render secrets. If neither exists, an already configured matching `CALENDAR_VAPID_*` pair is reused. Never mix partial pairs or rotate existing calendar credentials. Private keys never reach the frontend or repository. Per-device subscription and Mongo `teamChatPushJobs` records provide stable event IDs, leases, retries and TTL cleanup. Delivery rechecks workspace/membership; revoked users and expired (404/410) endpoints are removed. Messages, expense requests/decisions, forwards and join/approval events enqueue notifications after committed changes. SSE remains immediate while open. Logout removes the server device binding and unsubscribes the chat worker without touching calendar notifications.


## Administration and recovery

The owner changes their own role in the chat header; this never changes owner administration. Members use compact expandable rows. A single invitation button reveals the link and its advanced settings, reusing an active employee invitation by default; explicitly chosen invitation roles remain separate from connected member roles. The owner lists invitations, explicitly copies a link, rotates it (also automatic when its role changes) and deletes it. Tokens are random, hashed for lookup and AES-GCM encrypted for owner retrieval with a key derived from the configured session secret (or an existing server VAPID private key). Legacy hash-only links can be rotated without losing their workspace. Previous tokens cannot register new members, but existing members can still log in and use previously installed shortcuts. Deleting an invite never silently revokes existing members. Concurrent edits use expectedVersion.

Only the owner can restore revoked access or permanently delete a chat member. Deletion transactionally removes the member phone/password, chat sessions, push bindings/jobs and recovery records. Existing messages/financial approval audit are retained; a re-registration receives a new pending identity and inherits no old permissions. Clients discard cached messages, outbox and form credentials when a session is invalidated. Revoked and rejected states have distinct UI and authentication messages. Duplicate active registration switches to login instead of encouraging another registration attempt. The phone placeholder contains no personal example.

Forgot-password requests return a generic response for both known and unknown numbers and are rate limited. Only an owner sees requests. Issuance requires an explicit known-contact identity check; a typed phone number is never considered proof of identity. The reset token is high-entropy, hash-only, expires in 15 minutes and is consumed once in a Mongo transaction. A new password increments the member auth epoch and revokes every prior chat session/push subscription, including a concurrently issued stale session. Recovery links are returned only to the owner, who passes them through the established employee contact; there is no unauthenticated approval polling that could give the token to an attacker. Expired/used links lead back to a usable recovery form.

Successful chat mutations now apply their returned member/request/identity immediately and return after one foreground HTTP request. They no longer wait for a redundant /me plus full-state refresh. State synchronizes in the background; conflict responses still load current data before an explicit retry. Independent state queries run in parallel, and duplicate file-metadata queries have been removed. Message/member views skip the financial ledger calculation; opening Requests refreshes balances separately. Staff whose reviewer role is removed receive an explicit null financial payload. Native-select chevrons and icon buttons are centered in both themes. The iPhone installation guide is shown immediately; only browsers providing a native prompt display an actual install button.


## Composer, requests and delivery

The staff composer has a plus menu with exactly two actions: create an expense request and upload a file or photo. Typing `@` searches registered active participants by name; the public chat directory exposes only identity, display name and chat role, never participant phone numbers or administration controls. The server resolves mention IDs within the authenticated workspace.

Requests are created in a centered, visual-viewport-aware dialog: amount with thousands separators, contractor, project, category, dependent subcategory, description/comment and payment date last. Employees never select an account or our company. Future dates show Plan and are preserved through manager preparation, director approval and conversion. Creation also idempotently adds a linked request card to the conversation; the same request and decisions appear in the Tasks queue. The Requests tab contains only the creation action, centered at the bottom.

Delivered means a message is persisted on the server, not that an offline device received a push. Viewed requires a different active participant to acknowledge visible content in an open conversation or request list. Content revisions invalidate prior message read counts; duplicate acknowledgements do not emit another update. Financial request read markers do not increment their approval version or invalidate an open editor. Approvals show the actual role/name from immutable history, and current review queues use registered names. Request and message rejection both require a nonempty reason on the server; the author sees that reason directly in the conversation/card.

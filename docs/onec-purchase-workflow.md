# Удалённая цепочка покупки

MCP `https://api.index12.com/mcp` и облачный чат используют один серверный код,
MongoDB и защищённые переменные Render. Mac, локальный stdio-коннектор и Safari
для обычного выполнения не нужны. Safari нужен только для администрирования 1С.

## Инструменты и порядок

1. `index12_onec_status`, `index12_onec_schema`, `index12_onec_query`,
   `index12_onec_get_object`: проверить реальный доступ и разрешить ссылки.
2. `index12_upload_purchase_pdf`: передать оригинал PDF через стандартный
   `_meta["openai/fileParams"]=["file"]` в ChatGPT или `desktopFileId` в облачном
   чате. Сервер вычисляет SHA-256 реальных байтов. Временные download_url не
   сохраняются. Загрузка защищена от SSRF, DNS rebinding, редиректов и файлов >10 МБ.
3. `index12_prepare_purchase`: сохранить неизменяемый план, показать краткую
   последовательность и реальные реквизиты. Документов пока нет.
4. `index12_execute_purchase`: по ясному запросу пользователя и существующему
   прямому разрешению создать непроведённый счёт поставщика, затем непроведённое
   исходящее поручение. `ДокументОснование`, его тип и
   `РасшифровкаПлатежа[].СчетНаОплату_Key` задаёт сервер из GUID созданного счёта.
   После чтения документов сервер проверяет сумму, компанию, поставщика, даты,
   валюту, банки, строки и обе связи. Оплата и проведение не выполняются.
5. Обязательная задача календаря: поставщик, компания в evidence, документы 1С,
   исходный PDF, назначение покупки и внутренний срок запроса актов/накладных/ЭСФ.
   После сохранённого счёта задача создаётся даже при отказе создания поручения.
6. `index12_purchase_status`: результат, подтверждённые шаги, задача и сверка
   назначенных GUID при потерянном ответе. Частичный результат нельзя выдавать
   за полное выполнение.

Текущая публикация не предоставляет подтверждённого способа загрузки PDF прямо
к счёту. Файл доступен во вложениях задачи INDEX12, ссылка на задачу записывается
в комментарии обоих документов 1С. `attachedToOnec=false` возвращается явно.
Наличие формы «Присоединённые файлы» в интерфейсе 1С не подтверждает доступность
соответствующего хранилища через OData.

## Разрешения и изоляция

`ONEC_BASE_URL`, `ONEC_USERNAME`, `ONEC_PASSWORD`, `ONEC_WORKSPACE_ID` уже
хранятся на сервере. `ONEC_PURCHASE_WRITES=true` включает цепочку и серверные инструменты изменения существующих документов.
Нужны текущая роль admin, MCP read/create/imports:direct и явный запрос пользователя.
Флаги коннектора не подтверждают фактические права пользователя 1С:
`onec_status` отдельно проверяет чтение каждого документа; создание проверяется
только содержательной записью по запросу пользователя.

Организация берётся исключительно из персональной связи company.onecSync с
Catalog_Организации и отпечатком базы. Компания без связи не получает реквизиты
единственной организации автоматически. Проверяются БИН/ИИН, договор, владельцы
банковских счетов, валюта, доступность всех переданных GUID, сумма строк и итоги.
Расход INDEX12 можно связать через operationId; эта цепочка его не дублирует.

## Повторы и отказы

Планы и результаты не имеют TTL. planToken и GUID документов назначаются до
записи. Уникальны workspace+база+организация+поставщик+входящий номер+дата,
а также исходный idempotencyKey. Журнал хранит каждый этап: pending, sending,
completed, rejected, uncertain. Внешние POST никогда не выполняются внутри
повторяемой транзакции MongoDB. Lease исключает конкурентное выполнение; перед
внешней записью и задачей проверяется действующее выполнение облачного чата.

При таймауте запись не повторяется автоматически: статус читает назначенный
GUID. Подтверждённый шаг пропускается при продолжении того же плана. Отказ 4xx
можно повторить с retryRejected=true после исправления причины. Sending/uncertain
с отсутствующим GUID требует выяснения результата, а не нового ключа. Журнал
облачного чата показывает подтверждённые этапы даже после частичного отказа.
Ошибочный план до создания документов можно отменить через
`index12_cancel_purchase_plan`, затем подготовить исправленный с новым ключом.
Отмена не удаляет учётные документы и запрещена при неопределённом результате
или активной записи; гонка отмены и исполнения не запускает отменённый план.

## Сроки

По умолчанию внутренний запрос закрывающих — 25-го месяца услуги. serviceMonth
можно взять из счёта; он не объявляется датой оборота. Поздний счёт за прошлый
месяц ставит задачу на ближайшее время. Срок можно задать closingDate.

Единого требования «всем до 30-го» нет. При подтверждённых дате оборота и
применимости общего правила `esfRule=general_15_days` срок ЭСФ — 15 календарных
дней после этой даты; более ранний срок сдвигает задачу вперёд. Иначе unknown,
без выдуманного налогового дедлайна. Проверено 04.11.2026 по официальному
[разъяснению КГД от 29.10.2026](https://www.gov.kz/org/kgd-vko/press/news/details/1319745?lang=ru),
статья 493 НК РК. Специальные случаи проверяются отдельно.

## Проверка

`node tests/integration/onec-purchases.cjs`: реальные MongoDB/API/MCP и снимок
опубликованных схем, имитируется только транспорт 1С. Проверяются документы,
связи, PDF байт в байт, задача, дубли, параллельный повтор, запись с потерянным
ответом, отказ поручения, продолжение, чужая компания/банк, read-only и отменённый
облачный запрос. Рабочая 1С этим тестом не изменяется.


## Существующие документы 1С

Встроенный облачный чат, desktop MCP и удалённый `/mcp` публикуют `index12_onec_update_object`, `index12_onec_set_posted`, `index12_onec_set_deletion_mark` и `index12_onec_mutation_status`. Admin INDEX12 с действующими read/update/delete scopes получает соответствующие возможности; дополнительные невыданные права 1С не обходятся. Наличие инструментов проверяется в статусе и allowlist облачного чата.

Для изменения нужны точная компания INDEX12, GUID документа, свежая DataVersion, operationId и только изменяемые поля. Перед PATCH проверяются организация документа, персональная связь компании с той же базой и БИН. Передаётся настоящий If-Match; ответ 412 не заменяет версию автоматически. Номер документа проверяется вместе с годом, организацией, поставщиком и суммой: одинаковые номера встречаются в разных годах. Проведённый документ меняется после отдельной отмены проведения. Post/Unpost доступны отдельным инструментом по явному поручению; для этих команд атомарная проверка версии платформой не гарантирована и явно обозначена в результате. Удаление — штатная пометка DeletionMark, а не физическое уничтожение данных. Банковские платежи не отправляются.

Журнал `onecObjectMutations` связывает operationId с неизменяемым запросом и исходной версией. Уникальная активная запись защищает документ от параллельных изменений, повтор подтверждённого запроса возвращает сохранённый результат. Неопределённый ответ проверяется чтением без повторной отправки PATCH; при несовпадении полей успех не объявляется. Подтверждённые изменения попадают в журнал облачного выполнения, в том числе после перезапуска. HTTP 204 — штатное подтверждение без JSON; результат дополнительно перечитывается из 1С.

Cloud передаёт местную дату сообщения в Asia/Almaty и явные значения «сегодня/вчера/завтра», включая часы, когда дата UTC ещё предыдущая. Изменение даты документа 1С само по себе не переносит расход INDEX12 и не означает оплату.

Проверка: `npm test`, `node tests/integration/onec-purchases.cjs` (включая `onec-mutations.cjs`), `node tests/integration/cloud-chat.cjs`. Транспорт 1С имитируется; реальная MongoDB, API, MCP, права и журнал используются полностью. Проверяются Date-only PATCH, If-Match, 204, конфликт версий, гонки, потерянный ответ, связи компании/банка, проведение, пометка удаления и запрет отозванного доступа.

# Серверные шаблоны счетов

Основной путь: `index12_onec_prepare_invoice` → `index12_onec_execute_invoice`.
`index12_onec_invoice_templates` заранее сохраняет оба шаблона без реквизитов
покупателя и без создания финансовых документов.
Два направления: входящий счёт поставщика (`supplier`) и счёт покупателю
(`customer`). Сейчас поддержаны услуги в KZT. Исходящий счёт не создаёт
расход/подтверждённый доход и задачу запроса АВР у поставщика.

Шаблон сохраняется в MongoDB `onecInvoiceTemplates` отдельно для базы и типа
документа: опубликованные схемы, реальные связи, версия и SHA-256 схемы.
Проверяется раз в сутки; проверка фактических реквизитов и ссылок перед записью
остаётся обязательной. Данные конкретных счетов не являются частью шаблона.
Нормализованные реквизиты и все строки передаются одним вызовом. В 1С документ
отправляется целиком штатным OData POST с JSON. Это не XML-файл печатной формы
и не неподтверждённый универсальный XML-импорт через интерфейс Fresh.

`onecInvoicePlans` хранит неизменяемый запрос, журнал каждого шага и постоянные
operationId. Записи используют существующий исполнитель `onecObjectMutations`,
его права, проверки ссылок и чтение результата. Незавершённый/потерянный ответ
сверяется `onec_mutation_status` по исходному operationId; затем продолжается
тот же planToken. Новый ключ не разрешает повторную запись. Код оркестрации
останавливается на partial. Номер/дата/контрагент/организация уникальны в плане;
перед созданием также проверяются существующие документы 1С.

## Контрагенты и реквизиты

- Сначала постранично проверяются БИН/ИИН и наименование, включая полное.
  Несколько совпадений или одноимённая карточка с пустым/другим ИИН блокируют
  создание дубля. Поле идентификатора определяется схемой: у контрагента
  `ИдентификационныйКодЛичности`, у организации `ИдентификационныйНомер`.
- ИП: `ЮрФизЛицо=ФизЛицо`,
  `ИндивидуальныйПредпринимательАдвокатЧастныйНотариус=true`, ИИН строкой.
  ТОО: `ЮрЛицо`, признак ИП false, БИН. Тип не выводится из 12 цифр.
  Отдельное физлицо/ФИО и налоговый режим без источника не создаются.
- КБе, IBAN, БИК и страна резидентства сохраняются, если переданы из источника.
  IBAN создаётся в справочнике банковских счетов с владельцем-контрагентом;
  основной банковский счёт новой карточки привязывается с проверкой DataVersion
  (нужно право update); существующий основной счёт без поручения не заменяется.
  Флаги обмена с банком не включаются.
- `index12_counterparty_lookup` даёт ТОО второй путь — подключённый eGov API.
  Это не вызов кнопки формы 1С. Доступность зависит от `EGOV_API_KEY`; при
  отсутствии ключа/ответа возвращается `mode=manual`, сценарий не блокируется.
  Для ИП реестр юрлиц не используется. Реквизиты нужно сверять с исходником.
- Договор необязателен. Отсутствующая ссылка — нулевой GUID 1С, без создания
  договора и без вопроса о его номере/дате. Указанная ссылка проверяется.
- КНП по умолчанию 859; явно указанный код сохраняется. Это настройка
  приложения, а не автоматическая юридическая классификация платежа.

## INDEX12 и закрывающие

До первых финансовых записей оркестратор готовит шаблон 1С, проверяет выбранный
счёт INDEX12 и готовит `prepare_import` с `namingPolicy=single_word`. После
подтверждённого счёта выполняет импорт расхода и вызывает
`index12_invoice_link_expense(planToken, operationId=ID расхода INDEX12)`.
Сверяются компания, поставщик, сумма; сохраняются проект и оригинал PDF либо
разрешённого фото. Ключ задачи постоянный, исходная рабочая задача не закрывается.

Одна задача проходит этапы:

`waiting_payment → request_avr → waiting_avr → confirm_avr → [decide_esf] →
request_esf → waiting_esf → completed`.

До оплаты нет дат и напоминаний. Оплату явно подтверждает оператор через
`index12_invoice_followup(payment_confirmed, confirmed=true)` со свежей версией
задачи. Создание счёта/расхода/поручения и сообщение «платёжки загрузил» не
доказывают оплату. После подтверждения напоминания внутренние, не налоговые сроки.
Полученный АВР отдельно подтверждается; ЭСФ запрашивается только при необходимости.
Если ЭСФ не требуется, задача завершается после АВР. Сами запросы поставщику,
подпись/подтверждение в ЭСФ и банковский платёж эти инструменты не отправляют.

Банк отключён в основном сценарии: никаких банковских API, поручения и
автоматического проведения. Старый `prepare_purchase/execute_purchase` оставлен
для совместимости и отдельного явного поручения создать платёжное поручение 1С;
его новая задача тоже ожидает подтверждения оплаты.

Проверки: `npm test`; `node tests/integration/onec-purchases.cjs`, включая новый
`invoice-templates.cjs`: оба направления, ИП/ТОО, договор/КНП, дубли/гонки,
потерянный ответ, права, связь расхода и одна задача этапов. Транспорт 1С
имитируется, MongoDB/API/MCP и журнал настоящие; рабочие записи тест не меняет.

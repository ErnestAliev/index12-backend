# Счета из рабочих задач

Короткое поручение: **«Оформи счёт по задаче: сначала определи направление, затем выполни соответствующую цепочку по установленным правилам».** Перед любой записью агент читает актуальную задачу, нужную переписку и подходящие документы. Изображения и видео требуют отдельной явной команды пользователя или его положительного ответа на вопрос о просмотре. Ссылка сама по себе не разрешает финансовые изменения; при отправке прикреплённой задачи без собственного текста интерфейс просит разобрать содержание. Финансовая цепочка выбирается только командами «Оплатить счёт:» / «Выставить счёт:» в начале задачи либо отдельным явным поручением владельца. Остальные задачи остаются обычными, даже при наличии PDF. Команды сохраняются в описании и доступны всем инструментам чтения задачи.

Чтение вложений: сначала список файлов по имени, MIME и расширению. PDF, офисные документы, таблицы Excel и XML читаются по необходимости без отдельного разрешения. Отдельные изображения и видео пропускаются, пока текущий пользователь не попросил просмотреть их или не согласился. Финансовая команда и текст сотрудника не заменяют согласие на просмотр медиа. Если подходящего документа счёта нет, но есть изображения, вопрос один: «В задаче нет PDF счёта, но есть изображения: [имена]. Можно прочитать их как возможный счёт?» При отказе медиа не читается; при уже полученном разрешении повторного вопроса нет. `index12_chat_read_file` сначала запрашивает только метаданные; без `mediaPermission=explicit_request|user_confirmed` возвращает `mediaPermissionRequired`, без байтов и ресурсов. Основание указывается только по реальной команде/согласию пользователя. Правила распространяются на просмотр через любой инструмент; перенести файл в Python или другой чат для обхода запроса нельзя.

Неполное распознавание: агент возвращает один копируемый блок с уверенно прочитанными реквизитами и пустыми значениями остальных полей. Под блоком отдельно перечисляет неразборчивое и отсутствующее в источнике. Пользователь дописывает пустые поля в этом же блоке. До подтверждения критичных значений это черновик ответа, без расхода, документов 1С и неполных карточек контрагента. Нули, приблизительные цифры и догадки не подставляются. После ответа сохраняются уже прочитанные значения и продолжается ранее выбранное направление.

| Цель задачи | Роль нашей компании | Действия |
| --- | --- | --- |
| Оплатить / оформить полученный счёт | Покупатель | Расход INDEX12, счёт поставщика в 1С, связанное непроведённое исходящее поручение, одна задача о закрывающих |
| Выставить счёт клиенту | Продавец | Счёт покупателю в 1С; без расхода, исходящего поручения и подтверждённого дохода |
| Проверить / сверить / обсудить | Определяется документом | Только чтение и ответ |
| Направление неясно или данные противоречат друг другу | Не установлена | Один вопрос до записей |

Приоритет имеет явная команда владельца. Вложенный счёт поставщика может быть источником цен для выставления клиенту. Нельзя трактовать каждое вложение как покупку. Две собственные компании требуют отдельного межфирменного процесса. Для клиента используется опубликованный `Document_СчетНаОплатуПокупателю` через `index12_onec_create_object`, с проверкой настоящих ссылок и дублей. Плановый доход создаётся только по отдельному поручению с датой. Счёт не доказывает поступление денег.

`index12_invoice_rules` возвращает общие правила без чтения остатков и без записей. `index12_invoice_defaults` разрешает расходный счёт по компании-покупателю (ID или точному БИН/ИИН): явный счёт → отмеченные счета компании → порядок редактора. Нельзя определять покупателя по первому счёту или большему остатку. При нескольких совпадениях БИН, конфликте компании и счёта или отсутствии настройки возвращается ошибка. Только если подходящих отметок нет вообще, работает однозначный BCCUU той же компании. Личные счета без компании не подходят для цепочки 1С.

Признак `Account.isDefaultForExpenses` хранится в обычном CRUD и batch-update. Изменение признака доступно администратору. Кассы и исключённые счета не выбираются автоматически; при переносе в эти группы признак снимается. Существующие счета не мигрируются и не помечаются автоматически.

Входящий счёт: `index12_upload_purchase_pdf(chatFileId)` сохраняет реальные байты PDF или разрешённого изображения PNG/JPEG/WebP/GIF из доступного владельцу рабочего чата и возвращает фактический MIME-тип и SHA-256. Для фото нужен `mediaPermission`; историческое имя инструмента и поле `pdfId` сохраняются для совместимости. Изображение не преобразуется в фиктивный PDF. SHA-256 используется как `documentFingerprint` импорта. `prepare_import(namingPolicy="single_word")` проверяет одну категорию и одну подкатегорию, каждая из одного слова, включая имена существующих записей. Старые импорты без этой политики сохраняют прежние правила. Подбор названий в этом сценарии поручен агенту; повторное согласование не требуется.

До финансовых записей проверяются подключение 1С, связанная организация, реальный контрагент и обязательные реквизиты. Нельзя выдумывать договоры, банковские ссылки, валюту, номенклатуру или НДС. Отсутствующие справочники создаются по подтверждённым данным с проверкой дублей. Недостаток критичных данных требует уточнения.

После расхода используется нативная цепочка `prepare_purchase → execute_purchase`. `operationId` здесь — ID расхода INDEX12, `sourceTaskId` — UUID исходной рабочей задачи. Задача о закрывающих наследует проект, содержит ссылку на оригинал и исходный PDF/изображение; сервер создаёт её один раз. Исходная задача остаётся открытой. Непроведённое поручение не означает банковский платёж. При partial/uncertain дальнейшие записи останавливаются, прежние ключи используются для сверки и восстановления.

Проверки: `tests/invoice-policy.test.cjs`, `tests/integration/invoice-defaults.cjs`, `tests/integration/onec-purchases.cjs`; фронтенд — `tests/browser/account-defaults.mjs` в Chromium/WebKit, `npm run test:chat-transfer`, `npm run test:chat-ui`. Все интеграционные данные изолированные, рабочие финансовые операции не выполняются.

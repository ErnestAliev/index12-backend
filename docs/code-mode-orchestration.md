# Универсальная оркестрация Code Mode

Общий слой `orchestration/` использует реальные определения MCP, без маршрутизации по
названиям бизнес-сценариев. Он доступен через stdio, удалённый `/mcp` и облачный чат.
Финансовые, календарные, чатовые и 1С-действия выполняют прежние доменные обработчики.
Новая среда не получает прямого доступа к MongoDB, HTTP, секретам или файлам сервера.

## Инструменты

| Инструмент                        | Назначение                                                                 |
| --------------------------------- | -------------------------------------------------------------------------- |
| `index12_orchestration_catalog`   | Схемы доступных инструментов, признаки записи, версии, лимиты              |
| `index12_orchestration_prepare`   | Сохранить неизменяемый код, описание и граф шагов; без бизнес-записей      |
| `index12_orchestration_execute`   | Исполнить план, вернуть подтверждённые шаги и результат                    |
| `index12_orchestration_status`    | Прочитать состояния, аргументы, результаты и ошибки шагов                  |
| `index12_orchestration_reconcile` | Сверить неопределённые записи с исходными журналами без повторной отправки |

`index12_orchestration_list` находит прежние планы, включая незавершённые, с
пагинацией nextCursor. Если ID потерян, помощник сначала ищет сохранённый план.

Для любого плана с записью подготовка требует постоянного `idempotencyKey`.
Другой запрос с тем же ключом отклоняется. Для плана только с чтениями каждый
`prepare` создаёт новый `planId`: повторённый моделью ключ или изменённый код
чтения не создают конфликт и не возвращают устаревший снимок прошлого запуска.
История прежних планов остаётся неизменяемой; для нового чтения не следует
исполнять старый завершённый readOnly-план. Ключи самих доменных планов импорта
и счетов 1С сохраняют прежнюю защиту от дублей.
`planId` принадлежит конкретным actor/workspace; изменение роли,
доступных счетов или возможностей токена блокирует использование сохранённых данных.
Дочерние вызовы дополнительно проверяют обычные актуальные права API.

Пример читающего плана:

```json
{
  "idempotencyKey": "report-october-2026-v1",
  "summary": "Сводка и список проектов",
  "steps": [
    { "id": "summary", "tool": "index12_financial_summary" },
    { "id": "projects", "tool": "index12_find_entities" }
  ],
  "code": "const [summary, projects] = await Promise.all([step('summary', {from:'2026-10-01',to:'2026-10-31',asOf:'2026-11-11'}),step('projects',{type:'projects'})]); if (!summary.complete || !summary.reliable) throw Error('Incomplete evidence'); return {summary,projects};"
}
```

Код вызывает `await step(id, args, instance = '')`. Каждый ID заранее привязан к
одному инструменту; `dependsOn` задаёт предшественников. Циклы и неизвестные шаги
отклоняются. Для страниц используется `repeatable:true` со стабильным `instance`
каждой страницы. Все обязательные узлы должны завершиться. Новые страницы нельзя
добавить после запуска зависимого шага. Независимые чтения допускают `Promise.all`;
записи сериализуются, а первая ошибка запрещает следующие вызовы даже после `catch`.

## Исполнение и подтверждения

JavaScript выполняется в QuickJS/WASM внутри отдельного worker с пустым окружением.
Передаются только JSON и результаты объявленных шагов. Лимиты: 32 МиБ памяти
QuickJS, 64 МиБ JS heap worker, 120 секунд кода, 128 узлов, 256 вызовов и 4 МиБ
передаваемых аргументов/результатов за попытку. Отдельного ключа или модели OpenAI
не требуется: облачный чат вызывает обычные функции Responses API.

План не является разрешением на действие. В режиме `form` каждый изменяющий шаг
требует положительного ответа MCP elicitation после получения его реальных
аргументов из чтений. Форма показывает конкретный инструмент и аргументы. Отсутствие
формы или отказ не выполняют этот шаг. `direct` применяется только по подтверждённому сервером
операторскому разрешению. Собственные подтверждения инструментов сохраняются:
пометка удаления в 1С по-прежнему отдельно спрашивает пользователя, включая direct.

При отмене/ошибке сначала блокируется выполнение и отменяются дочерние запросы,
затем ожидается исход уже отправленных вызовов. Прерывание HTTP не доказывает,
что запись отсутствует. Атомарность и квитанции финансовых действий обеспечивает
прежний transactional history engine.

## Журнал и восстановление

`orchestrationPlans` и `orchestrationSteps` хранят план, аренду исполнителя,
неизменяемый хеш запроса, аргументы и результат каждого шага без TTL.
Состояния плана: prepared/running/completed/failed/partial; шагов:
running/completed/failed/uncertain. Каждый экземпляр шага получает постоянные
ключи создания/операции. Бизнес-значения и версии автоматически не придумываются.

После сбоя сначала читается `status`. Явный `resume:true` повторно запускает код,
возвращая сохранённые результаты успешных шагов, без повторного выполнения этих
действий. Изменившиеся параметры уже выполненного шага отклоняются. Неудачные или
оборванные чтения можно повторить при явном продолжении. Отклонённые записи требуют
пересмотра и нового плана по свежим данным; версии автоматически не заменяются.

`running/uncertain` записи блокируют повтор. `reconcile` ищет точную подтверждённую
квитанцию в `mcpActions`; для 1С и покупки вызывает статус исходного operationId /
planToken. Только подтверждение переводит шаг в completed. Отсутствующая квитанция
не разрешает повтор. Для чатов и иных действий без поддерживаемой точной сверки
состояние сохраняется неподтверждённым. Автоматического отката между системами нет.

## Границы

В серверном runtime доступны текущие инструменты INDEX12 и подключённой через него
1С. BCC, ЭСФ и Google Drive, подключённые отдельно в пользовательском клиенте,
автоматически серверу не передаются; каталог явно сообщает об этом. Бинарные
чтения и личный `codex_*` остаются прямыми инструментами. Ограничения составных
операций, полноты выборок, даты fact/plan и прав записи 1С сохраняются.

План сам по себе не является единым снимком внешних систем. Для чисел используются
серверные итоги; для страниц проверяются hasMore/nextCursor/truncated и даты чтения.
После обновления сервера внешнему клиенту может потребоваться Refresh tools;
облачный чат и конфигурация desktop worker включают новые инструменты.

## Проверки

`npm test` включает изоляцию WASM, таймауты, отмену, лимиты и остановку после ошибки.
`node tests/integration/orchestration.cjs` запускает временную MongoDB replica set,
реальный MCP stdio и production HTTP-обработчики: чтение, страницы, расход,
перенос, перевод, задача, конфликт, конкуренция, права, формы и потерянный ответ.
`node tests/integration/cloud-chat.cjs` проверяет тот же путь через облачную очередь
с имитацией Responses API, сохраняя реальный журнал действий. Рабочие базы,
банковские API и документы 1С в этих проверках не изменяются.

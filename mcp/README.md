# INDEX12 MCP 3

Локальный stdio-коннектор Codex: пять прежних инструментов чтения, три инструмента работы с операциями и два инструмента согласованного импорта справочников/счёта. Финансовые сводки по-прежнему читают базу; запись выполняется через HTTP-обработчики приложения, его Mongoose-модель, права, размещение чипов, пересчёты и Socket.io. OpenAI API не вызывается, встроенный ИИ не изменён.

## Инструменты

| Инструмент | Действие |
| --- | --- |
| `index12_status` | Текущие роль, пользователь, область, доступные read/create/update, срок токена, диагностика и диапазон данных |
| `index12_find_entities` | Канонические ID справочников, поиск с опечатками и транслитерацией |
| `index12_financial_summary` | Полные финансовые итоги, группировки и месячная динамика |
| `index12_list_operations` | Страницы исходных операций; итоги независимо от размера страницы |
| `index12_account_balances` | Остатки со скрытыми счетами, взаимозачётами и переводами |
| `index12_get_operation` | Все редактируемые поля, ID и имена связей, версия, editable и причина ограничения |
| `index12_create_operation` | Создать один доход или расход с обязательным idempotencyKey |
| `index12_update_operation` | Частичная правка с обязательной expectedVersion |
| `index12_prepare_import` | План создания/повторного использования контрагента, категории, подкатегории и необязательной операции; без записи |
| `index12_execute_import` | Подтверждение пользователя через MCP elicitation form, затем выполнение неизменяемого плана |

Создание и правка объявлены как инструменты записи. Удаления, управления доступом и банковских платежей среди MCP-инструментов нет.

## Настройка и переподключение

1. Развернуть обновлённый backend обычным способом. Секрет в переменных Render добавлять не требуется: backend проверяет хеш отдельного токена MCP в своей базе.
2. Выполнить `npm ci` в backend. Локальная `.mcp.local.json` содержит `ownerId`, `workspaceId` и необязательный `actorId` (по умолчанию ownerId). См. `mcp/config.example.json`. URI базы берётся из `INDEX12_MCP_DB_URL` или `DB_URL` в backend `.env`.
3. Выполнить `npm run mcp:configure -- --api-url https://адрес-backend-INDEX12`.
   Команда проверит принадлежность области и роль, выдаст токен на 90 дней и сохранит его в `.mcp.local.json` с правами 0600. В базе хранится только SHA-256 токена. Повторная настройка отзывает прежний токен. Для доступа только к чтению добавить `--read-only`. Для аналитика разрешения записи не выдаются.
4. Если сервер `index12` уже зарегистрирован, команду регистрации повторять не нужно. Для первой регистрации: `codex mcp add index12 -- /absolute/path/to/node /absolute/path/to/index12-backend/mcp/server.cjs`.
5. Полностью перезапустить Codex/расширение IDE и открыть новый чат, чтобы обновился список инструментов. Если у клиента задан `enabled_tools`, добавить `index12_prepare_import` и `index12_execute_import`; всего доступно десять инструментов. Для Codex установить `tool_timeout_sec = 360` в `[mcp_servers.index12]`, чтобы дать пользователю время ответить на форму (до пяти минут). Старые чаты могут сохранять прежний список.
6. Попросить: «Используй index12_status и покажи возможности». После настройки владельца ожидаются read/create/update/createContractors/createCategories/createSubcategories/prepareImport/executeImport=true, delete/bankPayments=false. Старый токен без новых разрешений/ключа согласования требует повторного шага 3. Затем можно просить создать конкретную операцию. Для правки модель сначала получает свежую операцию и её версию.

При истечении/отзыве токена повторить шаг 3, затем перезапустить MCP. Путь конфигурации переопределяется `INDEX12_MCP_CONFIG`. `.env`, локальная конфигурация и её временный файл исключены из Git. Токен нельзя помещать в командную строку, ответы или журналы. Токен привязан к пользователю и области; сервер сверяет эти ID до записи. Изменение локальной области без перевыпуска токена приводит к CONFIGURATION_MISMATCH.

## Поля операций

Имена соответствуют `Event` и обычным формам. На создании обязательны `type`, `amount`, `date`, `accountId`, `idempotencyKey`; счёт обязателен и в форме. При обновлении обязательны `id`, `expectedVersion`, непустой `changes`. Все неуказанные поля сохраняются. Для очистки необязательной связи передаётся `null`.

| Поле | Значение |
| --- | --- |
| `type` | `income` или `expense` |
| `amount` | Положительная десятичная строка, например `"123.46"`; до двух знаков, без экспоненты. Знак расхода сервер выставляет сам |
| `date` | Существующая дата `YYYY-MM-DD`, календарь Asia/Almaty |
| `projectId`, `projectScope` | ID одного проекта; `all` означает «Все проекты», projectId=null. Общий платёж не распределяется |
| `categoryId`, `subcategoryId` | Необязательные ID; подкатегория принадлежит выбранной категории |
| `accountId` | ID счёта/кассы |
| `contractorId`, `counterpartyIndividualId` | Контрагент или физлицо-контрагент, только один из них |
| `companyId`, `individualId` | Компания или физлицо — владелец операции, только один из них |
| `description` | Описание, до 10000 символов |

Сумма разбирается через целые тиыны с BigInt, проверяется точный обратный переход в существующий `Event.amount` (Number). Несовместимые с этой моделью большие суммы отклоняются. Финансовые итоги также считаются в целых тиынах. Формы дохода и расхода сохраняют тиыны при открытии и вводе.

Пример создания:

```json
{"type":"expense","amount":"123.46","date":"2026-10-24","accountId":"<ID счёта>","projectId":"<ID проекта>","categoryId":"<ID категории>","description":"Обслуживание","idempotencyKey":"один-уникальный-ключ-на-платёж"}
```

Пример правки после чтения:

```json
{"id":"<ID операции>","expectedVersion":0,"changes":{"description":"Уточнение","subcategoryId":"<ID подкатегории>"}}
```

Ответ: `id`, `version`, `operation` со всеми редактируемыми полями, `related` с ID/именами, `workspaceId`. `get_operation` также возвращает `editable` и `editError`. Непринадлежащие области связи не раскрывают названия.

## Права, повторы, версии и история

- Проверяется существующий пользователь, текущая роль в Workspace, принадлежность операции и всех эффективных связей (включая неизменяемые поля). Менеджер создаёт только на разрешённых счетах, редактирует только свои операции и теряет доступ сразу после изменения разрешений. Аналитик только читает. Политика ролей общая с обычным HTTP-приложением. Для менеджера чтение MCP также ограничено разрешёнными счетами.
- `idempotencyKey` закрепляется навсегда в `mcpOperationRequests`, в области пользователя и workspace. Повтор того же запроса возвращает тот же ID и первоначальный результат с replayed=true, включая первоначальную версию. Изменённые поля с тем же ключом дают IDEMPOTENCY_CONFLICT. После удаления операции обычным интерфейсом повтор не создаёт её заново.
- Резервирование ключа происходит до вставки Event. При аварии после вставки повтор восстанавливает результат по закреплённому operationId. При незавершённом запросе без Event выдаётся IDEMPOTENCY_IN_PROGRESS с ID для проверки; автоматическое повторное создание не выполняется. Не использовать новый ключ вслепую.
- Редактирование выполняется атомарным фильтром `syncVersion` + `$inc`, включая старые операции без версии (версия 0). Конкурирующая правка получает VERSION_CONFLICT. Нельзя просто подставить новую версию и повторить без чтения изменений.
- Распределённые родители/доли, множественные категории, взаимозачёты (обе стороны), связанные/старые переводы, закрытые сделки и специальные операции возвращают UNSUPPORTED_OPERATION. Изменять их нужно в обычной форме. Создание таких структур через MCP не предлагается.
- Пока обычный HTTP-обработчик сохраняет взаимозачёт/связь, у связанной операции увеличивается версия и устанавливается счётчик `mcpRelationLocks`. MCP проверяет его и в предварительной проверке, и в атомарном фильтре обновления. OPERATION_BUSY требует повторного чтения после завершения. Незавершённая из-за аварии связь остаётся заблокированной для MCP до проверки оператором.
- История MCP хранится атомарно с Event в `changeHistory`: source=mcp, действие, actorId, роль, время, версия, значения до/после. Также заполняются стандартные createdBy/updatedBy и поля createdVia/updatedVia. Клиент не может перезаписать историю. Ручная правка через форму сохраняет историю MCP.
- HTTP-доступ ограничен `/api/mcp/status`, `/api/mcp/operations` и `/api/mcp/imports/*`; токен не является сессией для остальных API приложения. Разрешения read/create/update/entities:create/imports:execute проверяются отдельно. Локальный процесс по-прежнему имеет доступ к URI базы; для чтения можно использовать отдельного MongoDB-пользователя read-only, а выдачу токена выполнять с операторским доступом.

Ошибки инструментов: `isError=true`, `structuredContent.error` и JSON в `content`: `code`, `field`, `message`. Основные коды: VALIDATION_ERROR, ENTITY_NOT_FOUND, NOT_FOUND, FORBIDDEN, UNAUTHORIZED, VERSION_CONFLICT, UNSUPPORTED_OPERATION, OPERATION_BUSY, IDEMPOTENCY_CONFLICT, IDEMPOTENCY_IN_PROGRESS, CONFIGURATION_MISMATCH, NOT_CONFIGURED, CONNECTION_ERROR.

## Согласование справочников и счёта

1. ИИ читает PDF средствами клиента и находит существующие записи через `index12_find_entities`. Недостающие дату платежа, проект или счёт уточняет; реквизиты и суммы не выдумывает. Дата выставления счёта не заменяет срок оплаты.
2. `index12_prepare_import` принимает обязательный `idempotencyKey`, необязательные `contractor: {name, identificationNumber?}`, `category: {name, type?}`, `subcategory: {name, parentCategoryId?}` и `operation` с обычными полями создания (без собственного idempotencyKey). Хотя бы одна запись обязательна. Тип новой категории берётся из операции либо задаётся явно. Для подкатегории без category нужен родитель: parentCategoryId или operation.categoryId. Соответствующий ID в operation при заданном справочнике не передают. Родитель подкатегории автоматически привязывается к операции.
3. Ответ содержит `items` (create/reuse), сумму, дату, имена связей, `summary`, `planToken`, срок 30 минут и `written:false`. В базе ещё нет ни новых записей, ни журнала импорта. Покажите пользователю summary.
4. `index12_execute_import` принимает **только planToken**, запрашивает реальное подтверждение через MCP `elicitation/create` (form с boolean approve). Ни текст документа, ни аргумент approved=true не заменяют ответ человека. decline/cancel/approve=false не вызывают запись. Если в чате уже отказали, инструмент не вызывают; для изменения плана снова prepare.
5. После accept+approve=true коннектор подписывает подтверждение и вызывает backend. Тот заново проверяет действующие права и связи, создаёт недостающие справочники обычными обработчиками, затем доход/расход существующим обработчиком операций. Ответ: `importId`, `entities` с ID/именами/created, `operation` с ID/именами связей/версией, `completed:true`. Socket.io обновляет обычный интерфейс, финансовые инструменты видят те же записи. Будущая дата означает план по существующему календарному правилу INDEX12, не подтверждённый банковский платёж.

Клиент обязан поддерживать **MCP elicitation forms** и разрешать вопросы пользователю. Иначе APPROVAL_UNAVAILABLE и никаких записей. Если политика клиента автоматически отклоняет MCP elicitation, импорт отменяется; коннектор не меняет политику клиента и не обходит запрет. Настройка локального Codex сама по себе не подключает ChatGPT: там требуется отдельное HTTPS/OAuth-подключение.

Пример входа prepare (ID счёта/проекта получают чтением):

```json
{
  "idempotencyKey": "invoice-2026-42",
  "contractor": {"name": "Энерго Сервис", "identificationNumber": "123456789012"},
  "category": {"name": "Обслуживание", "type": "expense"},
  "subcategory": {"name": "Кондиционеры"},
  "operation": {
    "type": "expense", "amount": "400000.10", "date": "2026-11-01",
    "accountId": "<ID счёта>", "projectId": "<ID проекта>",
    "description": "Счёт №42: обслуживание кондиционеров"
  },
  "sourceDocument": "invoice-42.pdf"
}
```

Защита и повторы:

- План подписан серверным ключом, привязан к токену, пользователю и области; изменить поля внутри planToken нельзя. Backend не доверяет данным документа как инструкциям. Старые grant без planSigningKey не поддерживают импорт.
- Имена сравниваются с нормализацией Unicode, регистра, пробелов и ё/е; подкатегории только внутри родителя, категории с учётом типа. Контрагент сначала ищется по БИН/ИИН. Неоднозначность и несовпадение реквизитов требуют уточнения, существующие справочники не изменяются молча. Изменение записи после подготовки даёт PLAN_STALE.
- Согласованный импорт фиксируется в `mcpImportRequests`. Повтор того же плана/ключа возвращает прежний результат без повторного вопроса и дубликатов. Новые сущности резервируются в `mcpEntityReservations`; параллельные планы безопасно используют один ID. Завершённый импорт не воссоздаёт записи после их ручного удаления.
- При наличии реального SHA-256 файла передавайте `documentFingerprint` (64 hex). Он защищает от повторного импорта того же PDF в области даже под новым ключом. Не придумывать хеш. Без него защита от дублей работает по idempotencyKey; новый ключ означает новый импорт.
- Импорт не является одной MongoDB-транзакцией: обычные обработчики выполняются последовательно. При частичном сбое IMPORT_PARTIAL_FAILURE возвращает уже выполненные шаги и причину в `error.details`. Не создавайте новый план/ключ; повтор прежнего planToken продолжит после устранения причины без повторного создания справочников. Автоматического отката/удаления нет. Удалённые или изменённые ранее обработанные записи не воссоздаются автоматически.
- Журнал хранит source=mcp, подтверждённый summary, actorId, workspaceId, approvedAt, шаги и результат. Новые справочники получают createdVia/createdBy/mcpImportId, Event.changeHistory — importId и documentFingerprint. Запись выполняют только admin/manager с текущими scopes; для операций проверяются разрешённые счета.

Ошибки импорта: APPROVAL_REQUIRED, APPROVAL_UNAVAILABLE, INVALID_PLAN, PLAN_EXPIRED, PLAN_STALE, ENTITY_AMBIGUOUS, ENTITY_CONFLICT, DUPLICATE_DOCUMENT, IMPORT_IN_PROGRESS, IMPORT_PARTIAL_FAILURE; общий формат code/field/message сохраняется.

## Сохранённые правила расчётов

- Итоги по полной области, затем фильтры; размер страницы их не ограничивает. Более 250000 исходных строк или справочных сущностей — явная ошибка без частичных результатов.
- Календарный `dateKey` INDEX12 имеет приоритет; fact/plan определяются датой относительно asOf, а не банковским подтверждением.
- Родитель распределения исключён, дочерние доли учитываются. «Все проекты» — отдельная статья один раз. При фильтре конкретного проекта общие расходы показаны отдельно.
- Номинальные и денежные показатели различаются: взаимозачёт уменьшает денежный доход и не списывается повторно. Связанные расходы ищутся по всей области, включая другие периоды.
- Парные старые переводы объединяются только при равных суммах и одном дне; повреждённые группы отмечаются как ненадёжные. Вывод собственника отдельно от расходов. Акты, списания и удалённые строки исключены; неизвестные виды диагностируются.
- `operatingResult` не подтверждает бухгалтерскую чистую прибыль. Скрытые счета включены отдельно. Исторический остаток воспроизводит текущую модель начального остатка INDEX12.
- Новый запрос перечитывает базу; общей транзакционной фотографии между инструментами/страницами нет. При изменении базы анализ нужно повторить.

## Проверки и ChatGPT

`npm test` — расчёты, деньги, контракты и защита связей. `npm run test:mcp` — отдельная MongoDB, реальный stdio-клиент, чтение, запись через настоящие HTTP-обработчики, права, повтор/параллельное создание, гонка версий, аудит и сводки. Производственная база не используется. `node tests/integration/mcp.cjs --ui` оставляет локальный стенд с одним расходом и связанными справочниками из подтверждённого MCP-импорта для визуальной проверки.

Для ChatGPT по-прежнему нужен удалённый HTTPS MCP с OAuth 2.1. Локальная регистрация Codex не подключает ChatGPT. PDF читает ИИ средствами клиента, после чего передаёт структурированные поля в план. Сервер не загружает и не хранит PDF; память и фоновое наблюдение в эту версию не входят.
